# PRD — نسخه‌ی اولیه‌ی Smartech Campaign Loop

**نسخه:** v5.0 · **تاریخ:** ۳۰ شهریور ۱۴۰۵ · **مالک محصول:** محسن علی‌پور · **سازنده:** مهدی اکبری
**مهلت:** ۳ تا ۴ روز · **دامنه:** هر سه ایستگاه، با ترتیب ساخت Verifier ← Designer ← Simulator

---

## ۰. سه تصمیم بنیادی این نسخه

**۱. ترتیب ساخت: Verifier اول.** در این نسخه، Verifier داده‌ی پیش‌بینی را **دستی** می‌گیرد. معماری‌اش طوری است که بعدا همان ورودی از Designer و Simulator بیاید، بدون بازنویسی.

**۲. Designer یک مشاور چنددیدگاهی است، نه یک بهینه‌ساز.** خروجی‌اش چند **اینسایت** از زاویه‌های مختلف است — از دید مدیر مالی، از دید مدیرعامل، از دید سگمنت، و غیره — و **انسان انتخاب می‌کند** کدام مبنای کمپین باشد. این مستقیما از `I-05` می‌آید: «اگر ابزار فقط کمپین را خودکار اجرا کند، اتوماسیون است؛ دستیار واقعی مثل یک تیم مشاور مارکتینگ، دیدگاه‌ها و سناریوهای متعدد می‌دهد.»

**۳. معماری هر سه ایستگاه دولایه است.** یک **موتور بهینه‌سازی** زیر، و یک **لایه‌ی هوش مصنوعی** رو. لایه‌ی زیر عدد می‌سازد؛ لایه‌ی رو آن عدد را از دید ذی‌نفعان مختلف روایت می‌کند، داشبورد می‌سازد و به پرسش جواب می‌دهد.

```
┌────────────────────────────────────────────────────────┐
│  لایه‌ی ۲ — هوش مصنوعی: تفسیر و ارائه                     │
│  اینسایت از دید ذی‌نفع · داشبورد · پاسخ به پرسش          │
│  ⛔ حق ساختن عدد ندارد                                  │
└────────────────────────────────────────────────────────┘
                        ▲  فقط عدد، با شناسه‌ی منبع
┌────────────────────────────────────────────────────────┐
│  لایه‌ی ۱ — موتور بهینه‌سازی: قطعی و تکرارپذیر            │
│  حل مسئله‌ی تخصیص تحت قیود · یک بهینه به ازای هر تابع هدف│
└────────────────────────────────────────────────────────┘
```

> **قاعده‌ی مرز دو لایه:** هر عددی که در متن یک اینسایت یا داشبورد ظاهر می‌شود باید شناسه‌ای داشته باشد که به یک خروجی مشخص لایه‌ی ۱ برگردد. **عددی که این شناسه را ندارد، نمایش داده نمی‌شود.**

**۴. در این نسخه، لایه‌ی ۲ قالب‌محور است، نه مدل زبانی.** جمله‌ها از قالب‌های از پیش نوشته‌شده ساخته می‌شوند و جای متغیرها با عدد لایه‌ی ۱ پر می‌شود. مدل زبانی کار نسخه‌ی بعد است (بخش ۱۰).

> ⚠ **تفکیکی که در دفاع باید گفته شود:** این نمونه **حلقه را نشان می‌دهد**؛ **ترتیب عرضه‌ی تجاری عوض نمی‌شود.** طبق تصمیم ۵ و فصل ۱۰، فروش هم از Verifier شروع می‌شود. نمونه‌ی اولیه اثبات مفهوم است، نه نسخه‌ی اول محصول.

## ۱. نقشه‌ی کلی — چه چیزی به چه چیزی وصل است

```
        داده‌ی اسمارتک              داده‌ی مرچنت
     (ادتریس / اینترک)        (کمپین‌های قبلی، اهداف، محدودیت‌ها)
              │                          │
              └────────────┬─────────────┘
                           ▼
                  ┌──────────────────┐
                  │   ایستگاه ۲      │
                  │    DESIGNER      │  ← ۱۰ اینسایت از ۱۰ دیدگاه
                  │  مشاور چنددیدگاه │
                  └────────┬─────────┘
                           │  انسان یکی را انتخاب می‌کند
                           ▼  plan_id
                  ┌──────────────────┐
                  │   ایستگاه ۳      │
                  │    SIMULATOR     │  ← قیف با بازه‌ی عدم‌قطعیت
                  └────────┬─────────┘
                           ▼  sim_id
                      [ اجرای واقعی ]
                           ▼  run_id
                  ┌──────────────────┐
                  │   ایستگاه ۱      │
                  │    VERIFIER      │  ← کارت انحراف + علت
                  └────────┬─────────┘
                           ▼  calibration_id
              به‌روزرسانی جدول نرخ‌ها ──────┘  (حلقه بسته شد)
```

**مسیر دستی (نسخه‌ی اول واقعی):** مرچنت پیش‌بینی خودش را مستقیم در Verifier وارد می‌کند و `plan_id`/`sim_id` خالی می‌ماند. این مسیر **حذف نمی‌شود** حتی وقتی دو ایستگاه دیگر ساخته شدند.

> **حداقل برای دمو: ۱۵ تا ۲۰ ردیف** در `campaign_history` تا نرخ‌ها معنادار باشند. زیر ۱۰ ردیف، اینسایت‌ها بی‌پشتوانه می‌شوند.

| فیلد | نوع | اجباری | اعتبارسنجی |
|---|---|---|---|

| `channel` | فهرست | ✓ | از فهرست `rates` |

| `actual_spend` | عدد | ✓ | بزرگ‌تر از صفر |

**ب) مسیر متصل — وقتی دو ایستگاه دیگر ساخته شدند**

| فیلد | منبع |
|---|---|
| `plan_id` | ایستگاه ۲ |
| `sim_id` | ایستگاه ۳ |
| پیش‌بینی‌ها | خودکار از `sim` خوانده می‌شود |
| نتیجه‌ی واقعی + دو پرچم کیفیت | همچنان دستی |

> `forecast_source` مهم‌ترین فیلد این ایستگاه است و **فرضیه‌ی `A3-02` را می‌سنجد**: آیا شرکت‌ها اصلا پیش‌بینی مکتوب دارند؟ در مسیر متصل، مقدارش خودکار «مکتوب و عددی» می‌شود.

### ۳.۲ منطق — درخت تصمیم انتساب علت

اولین شرطی که برقرار شود برنده است:

```
۱) data_complete = خیر  یا  tracker_matched = خیر
      → «ناسازگاری داده»
      → «تا رفع این مورد، انتساب علت معتبر نیست.»
      → توقف · کالیبراسیون اعمال نمی‌شود

۲) |انحراف بودجه| > ۱۵٪
      → «انحراف اجرا»
      → «بودجه‌ی مصرف‌شده با طرح نمی‌خواند؛ پیش از قضاوت درباره‌ی برآورد، اجرا بررسی شود.»
      → کالیبراسیون اعمال نمی‌شود

۳) |انحراف بودجه| ≤ ۱۵٪  و  نسبت (انحراف نصب ÷ انحراف بودجه) بین ۰٫۸ و ۱٫۲
      → «مقیاس، نه کیفیت»
      → «کمپین بزرگ‌تر یا کوچک‌تر از طرح اجرا شد؛ کارایی تغییر نکرده.»
      → کالیبراسیون اعمال نمی‌شود

۴) |انحراف بودجه| ≤ ۱۵٪  و  |انحراف نصب| > ۲۵٪
      → «خطای برآورد»
      → «بودجه طبق طرح خرج شد ولی خروجی نخواند؛ نرخ‌ها باید اصلاح شوند.»
      → ✅ کالیبراسیون اعمال می‌شود

۵) در غیر این صورت
      → «در دامنه‌ی انتظار»
      → ✅ کالیبراسیون اعمال می‌شود
```

**کالیبراسیون — فقط در حالت ۴ و ۵:**

```
cpi_جدید = (cpi_قدیم × sample_n + cpi_مشاهده‌شده) ÷ (sample_n + ۱)
cvr_جدید = (cvr_قدیم × sample_n + cvr_مشاهده‌شده) ÷ (sample_n + ۱)
sample_n  = sample_n + ۱
```

> ⚠ **ظریف‌ترین قاعده‌ی کل سیستم:** وقتی انحراف از **اجرا** یا از **مقیاس** آمده، نرخ کانال غلط نبوده. کالیبره‌کردن در آن حالت، حافظه‌ی سیستم را با نویز خراب می‌کند. اگر فقط یک چیز را دقیق پیاده کنی، همین است.

|---|---|---|---|---|
| `campaign_goal_type` | فهرست | مرچنت | ✓ | نصب · خرید · درآمد · نگهداشت |
| `campaign_goal_value` | عدد | مرچنت | ✓ | عدد هدف |
| `total_budget` | عدد | مرچنت | ✓ | بودجه‌ی این کمپین |
| `date_from` · `date_to` | تاریخ | مرچنت | ✓ | — |
| `allowed_channels` | چندانتخابی | مرچنت | ✓ | پیش‌فرض: همه‌ی کانال‌های `rates` منهای `blocked_channels` |
| `allowed_segments` | چندانتخابی | مرچنت | — | پیش‌فرض: همه |
| `risk_appetite` | فهرست | مرچنت | ✓ | محافظه‌کار · متعادل · تهاجمی |

| — | — | `campaign_history` | خودکار | عملکرد گذشته |

### ۴.۲ منطق — ده دیدگاه، یعنی ده تابع هدف

**این مهم‌ترین نکته‌ی Designer است:** هوش مصنوعی دیدگاه اختراع نمی‌کند. هر «دیدگاه ذی‌نفع» در لایه‌ی ۲، در لایه‌ی ۱ یک **تابع هدف متفاوت روی همان داده** است. لایه‌ی ۱ نقطه‌ی بهینه‌ی آن تابع را حساب می‌کند؛ لایه‌ی ۲ آن نقطه را به زبان کسی ترجمه می‌کند که آن تابع هدف را دارد.

| دیدگاه (لایه‌ی ۲) | تابع هدف (لایه‌ی ۱) |
|---|---|
| مدیر مالی | بیشینه‌سازی سود واحد، با قید `CAC ≤ gross_margin × aov` |
| مدیرعامل | بیشینه‌سازی حجم خروجی، با قید بودجه |
| مدیر بازاریابی | بیشینه‌سازی رتبه‌ی مرکب حجم و کارایی |
| تحلیل‌گر داده | کمینه‌سازی `variance` |
| مسئول کمپین | بیشینه‌سازی `sample_n` (آشنایی عملیاتی) |
| سگمنت پرارزش | بیشینه‌سازی `aov × cvr` |
| سگمنت در معرض ریزش | کمینه‌سازی هزینه‌ی جذب مجدد |
| فصلی | بیشینه‌سازی با ضریب فصلی تاریخی |
| رقابتی | بیشینه‌سازی خروجی با قید کمترین `sample_n` |
| محافظه‌کار | همان تابع هدف برتر، با قید `بودجه × ۰٫۲` |

**پیاده‌سازی در چهار روز:** هر تابع هدف یک تابع امتیازدهی ساده روی جدول `rates` است که ردیف‌ها را مرتب می‌کند و بودجه را تخصیص می‌دهد. ده تابع، ده مرتب‌سازی متفاوت. **این کل لایه‌ی ۱ است.**

جدول زیر جمله‌ی روایت هر دیدگاه در لایه‌ی ۲ را نشان می‌دهد — **قالب است، نه تولید آزاد متن:**

| # | دیدگاه | معیار انتخابش | جمله‌ی اینسایت (الگو) |
|---|---|---|---|
| ۱ | **مدیر مالی** | کانال×سگمنتی که `cpi ÷ cvr` (یعنی CAC) کمترین نسبت را به `gross_margin × aov` دارد | «از دید سود: روی {کانال} و سگمنت {سگمنت} تمرکز کن. CAC آنجا {عدد} است، یعنی {درصد} حاشیه‌ی هر سفارش — تنها ترکیبی که زیر سقف حاشیه‌ی شماست.» |
| ۲ | **مدیرعامل** | بیشترین حجم خروجی به ازای بودجه، صرف‌نظر از کارایی | «از دید رشد: {کانال} بیشترین حجم را می‌دهد — {عدد} نصب. CAC بالاتر است ولی اگر هدف سهم بازار است، این گزینه است.» |
| ۳ | **مدیر بازاریابی** | تعادل: رتبه‌ی مرکب حجم و کارایی | «از دید تعادل: تقسیم بودجه بین {کانال الف} و {کانال ب} — {درصد} و {درصد} — هم حجم می‌دهد هم CAC را زیر {عدد} نگه می‌دارد.» |
| ۴ | **تحلیل‌گر داده** | کمترین `variance` | «از دید قابلیت پیش‌بینی: {کانال} کمترین نوسان تاریخی را دارد (±{درصد}). اگر تصمیم بعدی به این نتیجه وابسته است، اینجا امن‌تر است.» |
| ۵ | **مسئول کمپین** | کانال با بیشترین `sample_n` (آشناترین) | «از دید اجرا: {کانال} را {عدد} بار اجرا کرده‌اید؛ سریع‌ترین راه‌اندازی و کمترین ریسک عملیاتی.» |
| ۶ | **سگمنت پرارزش** | سگمنتی با بالاترین `aov × cvr` | «از دید ارزش مشتری: سگمنت {سگمنت} ارزش سفارش {عدد} دارد — {نسبت} برابر میانگین. بودجه‌ی کمتر، بازگشت بیشتر.» |
| ۷ | **سگمنت در معرض ریزش** | سگمنت «در معرض ریزش» با `cvr` قابل‌قبول | «از دید نگهداشت: به‌جای جذب جدید، سگمنت در معرض ریزش را هدف بگیر — CAC جذب مجدد {عدد} در برابر {عدد} برای کاربر جدید.» |
| ۸ | **فصلی و مناسبتی** | اگر `seasonality_note` پر است یا بازه‌ی کمپین با اوج تاریخی هم‌پوشانی دارد | «از دید زمان‌بندی: بازه‌ی انتخابی با {دوره‌ی تاریخی} هم‌پوشانی دارد که در گذشته {درصد} بهتر بوده. جابه‌جایی {عدد} روزه را بررسی کن.» |
| ۹ | **رقابتی** | کانالی با کمترین سهم در `campaign_history` ولی نرخ قابل‌قبول | «از دید تمایز: {کانال} کمتر استفاده شده ولی نرخش قابل‌قبول است. فرصت کم‌رقابت‌تر.» |
| ۱۰ | **محافظه‌کار** | همان پیشنهاد دیدگاه برتر، ولی با ۲۰٪ بودجه | «از دید ریسک: پیش از تعهد کامل، {درصد} بودجه را روی {کانال} تست کن. هزینه‌ی یادگیری {عدد} است در برابر ریسک {عدد}.» |

**هر اینسایت این شش فیلد را دارد:**

| فیلد | توضیح |
|---|---|
| `perspective` | نام دیدگاه |
| `claim` | جمله‌ی اینسایت |
| `proposal` | پیشنهاد مشخص: کانال · سگمنت · تخصیص بودجه · بازه |
| `evidence` | عددی که از داده آمده و پشت ادعاست — **با ذکر تعداد کمپین پشتش** |
| `risk` | ریسک اصلی این انتخاب، یک جمله |
| `success_metric` | با چه عددی می‌فهمیم درست بود |

> ⚠ **فیلد `evidence` اجباری است و مکانیزم اجرای قاعده‌ی مرز دو لایه است.** هر عدد داخل `claim` و `proposal` باید در `evidence` شناسه‌ی منبعش را داشته باشد: کدام ردیف `rates`، با چند نمونه. اینسایتی که این شناسه را ندارد **رندر نمی‌شود**. این همان چیزی است که «مشاور» را از «حدس» جدا می‌کند — و در دفاع، جواب سؤال «هوش مصنوعی از کجا این را فهمید؟» است.

**مرتب‌سازی:** اینسایت‌ها بر اساس تناسب با `business_goal` و `risk_appetite` مرتب می‌شوند، ولی **هر ده‌تا نمایش داده می‌شوند**. فیلتر نکن — تنوع دیدگاه خودش ارزش است.

### ۴.۳ نقش انسان — انتخاب

کاربر یک اینسایت را **انتخاب** می‌کند، یا **ترکیب** می‌کند (تخصیص بودجه بین دو اینسایت). سپس می‌تواند تخصیص را دستی تغییر دهد.

**و دلیل انتخابش ثبت می‌شود** — فیلد `selection_reason`. این فیلد در دمو ساده به‌نظر می‌رسد ولی داده‌ای می‌سازد که هیچ‌جای دیگر نیست: **کدام دیدگاه‌ها در عمل انتخاب می‌شوند.** بعد از بیست کمپین، همین یک ستون می‌گوید مشاور واقعی چه زاویه‌ای دارد.

### ۴.۴ خروجی‌ها

| فیلد | نوع | توضیح |
|---|---|---|
| `plan_id` | متن | شناسه |
| `insights` | آرایه | هر ده اینسایت، ذخیره می‌شود |
| `selected_perspective` | متن | کدام دیدگاه انتخاب شد |
| `selection_reason` | متن | چرا |
| `allocation` | آرایه | `[{channel, segment, budget, share}]` |
| `expected_installs` · `expected_conversions` | عدد | از نرخ‌های همان ترکیب |
| `planned_cac` | عدد | `total_budget ÷ expected_conversions` |
| `goal_gap` | درصد | فاصله‌ی خروجی مورد انتظار تا هدف |

## ۵. ایستگاه ۳ — SIMULATOR

### ۵.۱ ورودی‌ها

| فیلد | نوع | منبع | اجباری |
|---|---|---|---|
| `plan_id` | متن | ایستگاه ۲ | ✓ |
| `allocation` | آرایه | `plan` | خودکار |
| نرخ‌ها و واریانس | عدد | `rates` | خودکار |
| `confidence_level` | فهرست | کاربر | — · پیش‌فرض ۸۰٪ |
| `external_factor` | فهرست | کاربر | — · عادی · فصل اوج · رکود · رقابت شدید |

`external_factor` یک ضریب ساده روی نرخ‌ها می‌گذارد (مثلا اوج ۱٫۱۵ و رکود ۰٫۸۵) و **مقدارش `فرض اثبات‌نشده` است** — روی صفحه هم همین نوشته شود.

### ۵.۲ منطق

```
برای هر ردیف تخصیص i:
    نصب_i              = بودجه_i ÷ cpi_i
    کران پایین نصب_i    = بودجه_i ÷ (cpi_i × (۱ + variance_i))
    کران بالا نصب_i     = بودجه_i ÷ (cpi_i × (۱ − variance_i))

    خرید_i              = نصب_i × cvr_i
    کران پایین خرید_i   = کران پایین نصب_i × cvr_i × (۱ − variance_i)
    کران بالا خرید_i    = کران بالا نصب_i  × cvr_i × (۱ + variance_i)

    درآمد_i             = خرید_i × aov

جمع همه‌ی ردیف‌ها  →  قیف کل
CAC پیش‌بینی‌شده  =  بودجه‌ی کل ÷ خرید کل
ROAS پیش‌بینی‌شده =  درآمد کل ÷ بودجه‌ی کل

حکم ریسک:
   کران پایین ≥ هدف              →  «هدف با اطمینان بالا پوشش داده می‌شود»
   مورد‌انتظار ≥ هدف > کران پایین →  «⚠ هدف در دامنه است ولی تضمین‌شده نیست»
   هدف > مورد‌انتظار              →  «⚠ با این بودجه هدف محقق نمی‌شود — کسری {عدد}»

حکم سودآوری:
   اگر CAC پیش‌بینی‌شده > gross_margin × aov
      →  «⚠ CAC از حاشیه‌ی هر سفارش بیشتر است؛ این کمپین در سطح واحد ضررده است»
```

> ⚠ **این شبیه‌سازی نیست، برون‌یابی نرخ تاریخی با بازه است — و همین جمله باید روی صفحه باشد:** «این پیش‌بینی از نرخ‌های تاریخی ثبت‌شده ساخته شده، نه از یک مدل. بازه‌ی نمایش‌داده‌شده از نوسان تاریخی همان کانال می‌آید.» نوشتن این روی خود محصول، در دفاع **امتیاز مثبت** است.

### ۵.۳ خروجی‌ها

| فیلد | نوع |
|---|---|
| `sim_id` | متن |
| `expected_installs` · `installs_low` · `installs_high` | عدد |
| `expected_conversions` · `conv_low` · `conv_high` | عدد |
| `expected_revenue` · `revenue_low` · `revenue_high` | عدد |
| `predicted_cac` · `predicted_roas` | عدد |
| `risk_verdict` · `profitability_verdict` | متن |
| `goal_coverage` | درصد — مورد‌انتظار ÷ هدف |

## ۶. صفحه‌ها — شش تا

| # | صفحه | محتوا |
|---|---|---|
| ۱ | **داده‌ها** | `rates` · `merchant_profile` · `campaign_history` — قابل ویرایش · ستون `sample_n` دیده شود |
| ۲ | **راستی‌آزمایی** | فرم مسیر دستی یا انتخاب `sim_id` ← کارت انحراف ← دکمه‌ی «اعمال کالیبراسیون» |
| ۳ | **طراحی — ورودی** | فرم هدف، بودجه، بازه، کانال‌ها، سگمنت‌ها، ریسک‌پذیری |
| ۴ | **طراحی — اینسایت‌ها** | **ده کارت اینسایت** با شش فیلد · انتخاب یا ترکیب · فیلد دلیل انتخاب |
| ۵ | **شبیه‌سازی** | قیف با بازه + دو حکم (ریسک و سودآوری) |
| ۶ | **حلقه** | زنجیره‌ی `plan_id → sim_id → run_id → calibration_id` + جدول «نرخ قبل / نرخ بعد» |
| ۷ | **داشبورد ذی‌نفع** | یک صفحه، با کلید تعویض دیدگاه — همان داده، از دید مدیر مالی یا مدیرعامل یا تحلیل‌گر · اگر وقت کم آمد، اولین صفحه‌ای است که حذف می‌شود |

### صفحه‌ی ۷ — داشبورد ذی‌نفع (اختیاری، ولی دمویی)

یک صفحه که **همان داده را از زاویه‌های متفاوت** نشان می‌دهد. کلید تعویض دیدگاه بالای صفحه:

| دیدگاه انتخاب‌شده | کارت‌هایی که نمایش داده می‌شوند |
|---|---|
| **مدیر مالی** | CAC در برابر سقف حاشیه · ROAS · سود واحد هر کانال · کمپین‌های ضررده |
| **مدیرعامل** | حجم کل خروجی · روند ماهانه · سهم هر کانال · فاصله تا هدف |
| **تحلیل‌گر داده** | پراکندگی پیش‌بینی در برابر واقعی · کانال‌های پرنوسان · کیفیت داده |
| **مسئول کمپین** | کمپین‌های در جریان · انحراف‌های باز · کارت‌های منتظر بررسی |

**این صفحه، مفهوم «لایه‌ی ۲» را در یک نگاه نشان می‌دهد:** هیچ عدد جدیدی ساخته نمی‌شود؛ فقط **همان اعداد، از زاویه‌ای که برای آن نقش معنا دارد** چیده می‌شوند.

### کارت اینسایت — صفحه‌ی کلیدی Designer

```
┌────────────────────────────────────────────────┐
│  👤 از دید مدیر مالی                            │
├────────────────────────────────────────────────┤
│  روی یکتانت و سگمنت «کاربر فعال» تمرکز کن.     │
│  CAC آنجا ۱۸۵٬۰۰۰ تومان است، یعنی ۴۲٪ حاشیه‌ی   │
│  هر سفارش — تنها ترکیبی که زیر سقف شماست.      │
├────────────────────────────────────────────────┤
│  پیشنهاد:  یکتانت · کاربر فعال · ۱۰۰٪ بودجه     │
│  شاهد:     CAC ۱۸۵ک از ۷ کمپین گذشته           │
│  ریسک:     حجم محدود — سقف این سگمنت ۳٬۰۰۰ نصب │

├────────────────────────────────────────────────┤

└────────────────────────────────────────────────┘
```

### کارت انحراف — صفحه‌ی کلیدی Verifier

```
┌──────────────────────────────────────────────────┐
│  کارت راستی‌آزمایی کمپین                          │
│  نام · کانال · سگمنت · بازه                       │
│  plan_id · sim_id · run_id                        │
├──────────────────────────────────────────────────┤
│  متریک    پیش‌بینی (بازه)      واقعی    انحراف    │
│  بودجه    ۵۰۰ م               ۵۲۰ م     +۴٪  ✓   │
│  نصب      ۱۰٬۰۰۰ (۸٬۳–۱۲٬۵ک)  ۶٬۸۰۰    −۳۲٪  ⚠   │
│  خرید     ۸۰۰   (۶۴۰–۱٬۰۰۰)   ۵۹۰      −۲۶٪  ⚠   │
├──────────────────────────────────────────────────┤
│  ⚠ علت محتمل: خطای برآورد                        │
│  بودجه طبق طرح خرج شد ولی خروجی نخواند.          │
│  واقعی حتی از کران پایین پیش‌بینی هم پایین‌تر بود.│
├──────────────────────────────────────────────────┤
│  دیدگاه انتخاب‌شده: مدیر مالی                     │
│  منبع پیش‌بینی: ایستگاه ۳ (sim_id)                │
│  کیفیت داده: کامل · شناسه‌ی ترکر: منطبق            │
│  ← کالیبراسیون: CPI یکتانت از ۵۰٬۰۰۰ به ۵۸٬۸۰۰   │
└──────────────────────────────────────────────────┘
```

**ردیف «دیدگاه انتخاب‌شده» روی کارت انحراف، ارزشمندترین جزئیات کل سیستم است:** بعد از بیست کمپین می‌شود پرسید **کدام دیدگاه بیشتر درست از آب درآمده** — و آن، هسته‌ی واقعی یادگیری این محصول است.

## ۷. معیار پذیرش

| # | معیار |
|---|---|
| ۱ | یک دور کامل حلقه زیر **۵ دقیقه** |
| ۲ | Designer **ده اینسایت** بدهد و هر کدام هر شش فیلد را داشته باشد |
| ۳ | هیچ اینسایتی بدون `evidence` عددی نمایش داده نشود |
| ۴ | دو اینسایت با ورودی یکسان، پیشنهاد متفاوت بدهند (اثبات تنوع دیدگاه) |
| ۵ | بازه‌ی Simulator همیشه: کران پایین < مورد‌انتظار < کران بالا |
| ۶ | حکم سودآوری وقتی CAC > حاشیه، هشدار بدهد |
| ۷ | **هر پنج شاخه‌ی Verifier** با داده‌ی نمونه درست عمل کند |
| ۸ | در «ناسازگاری داده»، «انحراف اجرا» و «مقیاس» کالیبراسیون **اعمال نشود** |
| ۹ | پس از کالیبراسیون، اجرای دوباره‌ی همان طرح عدد متفاوت بدهد |
| ۱۰ | مسیر دستی Verifier بدون `plan_id` کار کند |
| ۱۱ | کارت‌ها بدون شکستگی چاپ/PDF شوند |
| ۱۲ | داده با بستن مرورگر از بین نرود · همه‌چیز فارسی و راست‌چین |

**معیارهای ۳، ۴ و ۸ مهم‌ترین‌اند.** اگر اینسایت‌ها شاهد نداشته باشند یا همه یک چیز بگویند، Designer فقط یک فرم رنگی است.

## ۸. برنامه‌ی چهار روزه

| روز | کار | خروجی پایان روز |
|---|---|---|
| **۱** | جدول‌های داده + صفحه‌ی داده‌ها + **Verifier کامل** با درخت تصمیم و کالیبراسیون مشروط | هر پنج شاخه درست جواب می‌دهد |
| **۲** | **Designer** — ده تابع دیدگاه + کارت اینسایت + انتخاب و ثبت دلیل | ده اینسایت با شاهد تولید می‌شود |
| **۳** | **Simulator** — قیف با بازه + دو حکم + زنجیره‌ی شناسه‌ها | طرح انتخاب‌شده پیش‌بینی می‌گیرد |
| **۴** | صفحه‌ی حلقه + داده‌ی دمو + رفع اشکال + تمرین دمو | **آماده‌ی دفاع** |

**داده‌ی دمو:** ۱۵ تا ۲۰ کمپین تاریخی + چهار کمپین برای نمایش چهار شاخه‌ی متفاوت Verifier — «خطای برآورد» (کالیبره می‌شود)، «انحراف اجرا» (نمی‌شود)، «ناسازگاری داده» (متوقف می‌شود)، «مقیاس نه کیفیت».

**اگر عقب افتادی، به این ترتیب کم کن:**
۱. صفحه‌ی حلقه (زنجیره را دستی توضیح بده)
۲. ده دیدگاه → شش دیدگاه (۱، ۲، ۴، ۶، ۷، ۱۰ را نگه دار — متنوع‌ترین‌ها)
۳. `external_factor` در Simulator
۴. حالت ترکیب دو اینسایت

**هرگز حذف نکن:** درخت تصمیم Verifier · فیلد `evidence` اینسایت‌ها · کالیبراسیون مشروط.

## ۹. پیشنهاد فنی

| لایه | پیشنهاد |
|---|---|
| رابط | یک صفحه‌ی HTML با Vue یا React از CDN |
| ذخیره‌سازی | `localStorage` یا فایل JSON |
| چاپ | `window.print()` با `@media print` |
| فونت و جهت | وزیرمتن · `direction: rtl` روی `body` |

**بک‌اند نساز.** هیچ‌کدام از این قابلیت‌ها سرور نمی‌خواهند.

**لایه‌ی ۲ در این نسخه قالب‌محور است، نه مدل زبانی.**

وسوسه‌اش هست — «بگذار LLM اینسایت بنویسد» — ولی سه مشکل دارد: در دمو ممکن است عددی بگوید که پشتش داده نیست؛ خروجی‌اش تکرارپذیر نیست؛ و در دفاع نمی‌شود توضیح داد چرا آن جمله را گفت.

**ولی معماری باید طوری باشد که بعدا مدل زبانی جایش بنشیند، بدون بازنویسی.** یعنی:

```
لایه‌ی ۱  →  یک شیء JSON تمیز  →  لایه‌ی ۲
```

لایه‌ی ۲ فقط آن شیء را می‌خواند. امروز یک تابع قالب‌ساز آن را می‌خواند؛ فردا یک مدل زبانی با همان ورودی و همان قید «فقط از این اعداد استفاده کن». **اگر این مرز را از روز اول رعایت کنی، مهاجرت به مدل زبانی یک تعویض تابع است، نه یک بازنویسی.**

مثال شیء خروجی لایه‌ی ۱ برای یک دیدگاه:

```json
{
  "perspective_id": "cfo",
  "objective": "max_unit_profit",
  "constraint": "cac <= gross_margin * aov",
  "winner": { "channel": "yektanet", "segment": "active", "budget_share": 1.0 },
  "metrics": { "cac": 185000, "margin_pct": 0.42, "expected_conversions": 2700 },
  "evidence": { "source": "rates", "row": "yektanet|active", "sample_n": 7 },
  "risk": { "type": "volume_ceiling", "value": 3000 },
  "success_metric": { "metric": "actual_cac", "threshold": 220000, "direction": "below" }
}
```

## ۱۰. آنچه در دفاع گفته می‌شود — و آنچه نمی‌شود
