### ۰.۲ تصمیم‌های بنیادی (به‌روزشده)

**۱. ترتیب ساخت: Verifier اول.** بدون تغییر. مسیر دستی Verifier (بدون `plan_id`) **هرگز حذف نمی‌شود**.

**۲. Designer مشاور چنددیدگاهی است، نه بهینه‌ساز.** ده دیدگاه = ده تابع هدف روی یک داده. **انسان انتخاب می‌کند** و دلیلش را می‌نویسد (`I-05`).

**۳. معماری هر ایستگاه دولایه است.**

```
┌────────────────────────────────────────────────────────┐
│  لایه‌ی ۲ — روایت: قالب (پیش‌فرض) یا مدل زبانی متیس        │
│  اینسایت از دید ذی‌نفع · روایت علت · پاسخ به پرسش         │
│  ⛔ حق ساختن عدد ندارد · دیوار عدد سمت سرور               │
└────────────────────────────────────────────────────────┘
                        ▲  فقط شیء JSON لایه‌ی ۱ + source_ref
┌────────────────────────────────────────────────────────┐
│  لایه‌ی ۱ — موتور قطعی (packages/engine)                 │
│  تخصیص · پیش‌بینی · پایش · انتساب علت · کالیبراسیون       │
└────────────────────────────────────────────────────────┘
```

> **قاعده‌ی مرز دو لایه:** هر عددی که کاربر می‌بیند یک `source_ref` دارد که به یک ردیف `rates`، یک `plan`، `sim`، `run` یا `calibration` برمی‌گردد. **عدد بدون شناسه نمایش داده نمی‌شود.** مدل زبانی عدد نمی‌سازد؛ فقط عددی را که در ورودی‌اش آمده، عیناً تکرار می‌کند و سرور این را بررسی می‌کند (بخش ۱۱.۴).

**۴. (تغییر نسبت به v5) لایه‌ی ۲ دو پیاده‌سازی هم‌ارز دارد.** قالب قطعی پیش‌فرض است و همیشه کار می‌کند. وقتی `AI_PROVIDER=metis` و کلید موجود است، مدل زبانی همان شیء JSON را روایت می‌کند. اگر مدل خطا بدهد، دیر جواب دهد، یا عددی خارج از ورودی بگوید، خروجی‌اش دور ریخته و قالب نمایش داده می‌شود. **مهاجرت از قالب به مدل، یک تعویض تابع است، نه بازنویسی** — همان اصلی که v5 خواسته بود.

**۵. اتوماسیون تا مرز تصمیم.** هر چیزی که عدد است (همگام‌سازی، پایش، انتساب علت، پیش‌نمایش کالیبراسیون، گزارش) خودکار می‌شود. سه نقطه عمداً انسانی می‌مانند: **انتخاب دیدگاه + دلیل**، **تأیید نتیجه‌ی واقعی**، **اعمال کالیبراسیون**. (بخش ۱۲)

> ⚠ **تفکیکی که در دفاع باید گفته شود:** این محصول **حلقه را نشان می‌دهد**؛ **ترتیب عرضه‌ی تجاری عوض نمی‌شود.** فروش از Verifier شروع می‌شود.

## ۱. نقشه‌ی کلی حلقه

```
     داده‌ی اسمارتک (ادتریس / اینترک)      داده‌ی مرچنت (CSV / فرم)
                    │                               │
                    └──────────────┬────────────────┘
                                   ▼
              [ آماده‌سازی: داده‌ها · پروفایل · چک‌لیست آمادگی ]
                                   ▼
                      ┌─────────────────────────┐
                      │ ایستگاه ۲ — DESIGNER     │ ← ۱۰ اینسایت از ۱۰ دیدگاه
                      └────────────┬────────────┘
                انسان انتخاب/ترکیب می‌کند + دلیل  ▼  plan_id (نسخه‌دار)
                      ┌─────────────────────────┐
                      │ ایستگاه ۳ — SIMULATOR    │ ← قیف با بازه‌ی تجربی + POAS
                      └────────────┬────────────┘   + سناریوی «اگر…»
                                   ▼  sim_id
                      ┌─────────────────────────┐
                      │ پایش حین اجرا            │ ← هشدار + پیشنهاد جابه‌جایی
                      └────────────┬────────────┘   (همگام‌سازی روزانه)
                                   ▼  run_id (پیش‌نویس خودکار، تأیید انسانی)
                      ┌─────────────────────────┐
                      │ ایستگاه ۱ — VERIFIER     │ ← علت انحراف + اثر افزایشی
                      └────────────┬────────────┘
                   فقط در ۲ شاخه‌ی معتبر ▼  calibration_id (قابل بازگردانی)
                      [ به‌روزرسانی وزنی جدول نرخ ]
                                   ▼
                      [ بستن کمپین → دفترچه‌ی دیدگاه‌ها ] ──┐
                                   ▲                         │
                                   └──── حلقه‌ی بعد ◄────────┘
```

**مسیر دستی:** مرچنت پیش‌بینی خودش را مستقیم در Verifier وارد می‌کند؛ `plan_id` و `sim_id` خالی می‌ماند. این مسیر باقی می‌ماند.

## ۲. قراردادها

### ۲.۱ شناسه‌ها

| شناسه | الگو | قاعده |
|---|---|---|
| `plan_id` | `plan-{سال جلالی}-{seq}` | مثال: `plan-1405-101` |
| `sim_id` | `sim-{سال}-{seq}` | همان `seq` طرح |
| `run_id` | `run-{سال}-{seq}` | همان `seq` طرح؛ در مسیر دستی `seq` تازه |
| `calibration_id` | `cal-{سال}-{seq}` | همان `seq` |
| `campaign_history.id` | `ک-{شماره}` | ردیف‌های CSV از ۲۰۰ به بعد |

- `seq` برای هر فضای کاری یکتا و صعودی است و از **۱۰۱** شروع می‌شود؛ یک sequence در پایگاه داده، نه شمارنده‌ی سمت کاربر.
- **ویرایش طرح پیش از ثبت نتیجه** `seq` را نگه می‌دارد و `version` را یکی بالا می‌برد. طرح تازه `seq` تازه می‌گیرد.
- API شناسه را با رقم لاتین برمی‌گرداند؛ رابط کاربری با `formatFa()` فارسی نمایش می‌دهد (`plan-۱۴۰۵-۱۰۱`).

### ۲.۲ عدد، پول، تاریخ

- پول: **تومان صحیح** (`bigint`). نرخ‌ها `numeric(12,6)`.
- درصد: در API کسری ۰ تا ۱؛ در رابط ۰ تا ۱۰۰.
- رقم فارسی فقط در رابط، با یک تابع `formatFa()`. API رقم لاتین، تاریخ ISO + فیلد رشته‌ای `jalali`.
- قالب‌بندی پول در رابط (تابع `money` نمونه): ≥ ۱ میلیارد → «۱٫۵ میلیارد»؛ ≥ ۱۰ میلیون → «۵۰۰ م»؛ کمتر → «۲۸۲٬۰۲۵».
- انحراف با علامت: `signPct` → «+۴٫۰٪»، «−۳۲٪» (زیر ۱٪ دو رقم اعشار، زیر ۱۰٪ یک رقم، بالاتر بدون اعشار).
- ورودی عددی: رقم فارسی و لاتین، جداکننده‌ی `٬` و `,`، اعشار `٫` پذیرفته می‌شود (`toNum`).

## ۴. موتور مشترک — فرمول‌های پایه

همه‌ی توابع در `packages/engine`، بدون I/O، قطعی. نام تابع نمونه داخل پرانتز.

```
infl(r)        = (1 + inflation_monthly) ^ age_months
cpi_adj(r)     = round(unit_cost × infl(r))                                  (cpiAdj)
cac(r)         = cpi_adj(r) / cvr                                            (cac)
margin_cap(r)  = gross_margin × aov                                          (cap) — سقف CAC سودده
installs(r, B) = B / cpi_adj / (1 + 0.5 × B / max(ceiling × cpi_adj, 1))    (installsAt)
POAS           = (revenue × gross_margin − spend) / spend                    (poas) — اگر spend=0 → 0
```

**بازده نزولی:** وقتی بودجه دقیقاً به اندازه‌ی `ceiling × cpi_adj` باشد، نصب به **دوسوم** حالت خطی می‌رسد (آزمون موجود).

> ⚠ `ceo` در امتیازدهی از `unit_cost` **بدون** تعدیل تورم استفاده می‌کند (`1e6 / cpi`)؛ بقیه‌ی توابع از `cpi_adj`. این رفتار نمونه است و حفظ می‌شود مگر مالک محصول تصمیم دیگری بگیرد (بخش ۲۱).

### ۵.۴ تخصیص بودجه (`allocate`) — حریصانه با سقف حجم

```
ردیف‌های مجاز را با امتیاز دیدگاه نزولی مرتب کن.
rem = budget
برای هر ردیف به ترتیب:
    اگر rem ≤ 0.005 × budget → توقف
    b = min(rem, ceiling × cpi_adj)     ← ظرفیت ردیف
    ردیف با بودجه‌ی b به تخصیص اضافه شود؛ rem −= b
اگر rem > 0 → باقی‌مانده به ردیف اول اضافه شود
share_i = budget_i / Σ budget
```

**خروجی مورد انتظار هر تخصیص** (`expected`): جمع `installs(r, B_r)`، `conv = installs × cvr`، `revenue = conv × aov`؛ سپس `cac = budget / conv`، `roas = revenue / budget`، `poas`.
(توجه: `expected` در Designer تقلب را کم نمی‌کند؛ Simulator می‌کند. بنابراین «خرید مورد انتظار» کارت اینسایت می‌تواند کمی بیشتر از قیف Simulator باشد — بخش ۱۸.)

### ۶.۱ ورودی‌ها

### ۶.۲ تقویم مناسبت‌ها (`occasion`)

| مناسبت | اثر خرید `lift` | تغییر هزینه `cpi` |
|---|---|---|
| بدون مناسبت | ۰ | ۰ |
| یلدا (آذر) | +۱۲٪ | +۸٪ |
| بلک‌فرایدی (آبان) | +۳۵٪ | +۲۵٪ |
| نوروز (اسفند–فروردین) | +۲۸٪ | +۱۸٪ |
| ماه رمضان | −۸٪ | −۵٪ |
| بازگشایی مدارس (شهریور) | +۱۰٪ | +۶٪ |

در نسخه‌ی تولید، مناسبت از روی بازه‌ی کمپین خودکار پیشنهاد می‌شود وقتی ≥ ۵۰٪ بازه با آن هم‌پوشانی دارد (`BACKEND-SPEC` §۴).

### ۶.۳ منطق (`simulate`)

```
f = external_factor × (1 + occasion.lift) / (1 + occasion.cpi)
k = band_width

برای هر ردیف تخصیص i:
    v        = min(variance_i × k, 0.6)
    raw_i    = installs(r_i, budget_i) × f
    fr       = (paid ? fraud_i : 0)
    inst_i   = raw_i × (1 − fr)                    ← نصب تقلبی پیش از خرید حذف می‌شود
    conv_i   = inst_i × cvr_i
    s        = 0.85 × v

    installs: inst_i      · low inst_i × (1 − 0.7v)   · high inst_i × (1 + 0.7v)
    conv:     conv_i      · low conv_i × (1 − s)      · high conv_i × (1 + s)
    revenue:  conv_i×aov  · low ×(1 − s)              · high ×(1 + s)
    fraud_installs += raw_i × fr ؛  ret30 += inst_i × d30_i
    budget_paid / budget_owned بر اساس نوع

جمع ردیف‌ها → قیف کل
CAC      = budget / conv
AOV_w    = revenue / conv                        ← AOV وزنی
cap      = gross_margin × AOV_w                  ← حاشیه‌ی هر سفارش
ROAS     = revenue / budget
POAS     = (revenue × gross_margin − budget) / budget
payback  = CAC / (cap × 1.2)                     ← ماه؛ فرض ۱٫۲ سفارش در ماه
LTV/CAC  = ltv_avg / CAC                          (اگر LTV ثبت شده)
coverage = target / goal_value
target   = نصب → installs · درآمد → revenue · خرید و نگهداشت → conv
```

**حکم ریسک** (`t_low` = کران پایین متریک هدف):

| شرط | متن |
|---|---|
| `goal_value ≤ 0` | «عدد هدفی ثبت نشده؛ پوشش هدف قابل ارزیابی نیست.» |
| `t_low ≥ goal` | «هدف پوشش داده می‌شود — حتی کران پایین بازه‌ی تجربی از هدف بالاتر است.» |
| `target ≥ goal > t_low` | «هدف در دامنه است ولی تضمین‌شده نیست: مورد انتظار {target} در برابر هدف {goal}، کران پایین {t_low}.» |
| `goal > target` | «با این بودجه هدف محقق نمی‌شود — کسری {goal − target} {نوع هدف}. با بازده نزولی، افزایش بودجه کسری را خطی جبران نمی‌کند.» |

**حکم سودآوری (POAS):**

| شرط | متن |
|---|---|
| `POAS < 0` | «سود ناخالص پیش‌بینی‌شده از هزینه کمتر است (POAS {±}). CAC {x} در برابر حاشیه‌ی هر سفارش {cap} تومان — بازگشت فقط با خرید تکراری ممکن است (دوره‌ی بازگشت {payback} ماه).» |
| `POAS ≥ 0` | «سود ناخالص از هزینه بیشتر است (POAS {±}). CAC {x} زیر حاشیه‌ی هر سفارش {cap} تومان.» |

> `POAS < 0` معادل `CAC > gross_margin × AOV_w` است؛ پس هشدار v5 («CAC از حاشیه بیشتر است») همین‌جا پوشش داده می‌شود.

> ⚠ **جمله‌ی الزامی روی صفحه:** «این پیش‌بینی از نرخ‌های تاریخی ثبت‌شده ساخته شده، نه از یک مدل. بازه‌ی نمایش‌داده‌شده از نوسان تاریخی همان کانال می‌آید. این برون‌یابی است، نه شبیه‌سازی.» عبارت «فاصله‌ی اطمینان» یا «سطح اطمینان» هیچ‌جا به کار نمی‌رود.

## ۷. پایش حین اجرا (بین ایستگاه ۳ و ۱)

### ۷.۱ ورودی

«روز چندم کمپین»، «هزینه‌ی تجمعی»، «نصب تجمعی»، «خرید تجمعی». دستی یا از همگام‌سازی روزانه‌ی ادتریس/اینترک (`pace_snapshot`).

### ۷.۲ منطق

```
frac     = clamp(day, 1, D) / D          ← D در نمونه ثابت ۳۰؛ در تولید = طول واقعی کمپین (بخش ۱۸)
expected = sim × frac                     (برای هزینه، نصب، خرید)
dev      = actual / expected − 1
وضعیت ردیف: |dev| ≤ 15% ✓ · ≤ 30% ⚠ · > 30% ✕
```

| هشدار | شرط | متن |
|---|---|---|
| هزینه‌ی تند (bad) | `dev_spend > +20%` | «بودجه سریع‌تر از برنامه خرج می‌شود ({dev}). با این سرعت بودجه روز {round(D/(1+dev))} تمام می‌شود.» |
| هزینه‌ی کند (warn) | `dev_spend < −20%` | «بودجه کندتر از برنامه خرج می‌شود ({dev}). احتمالاً پیشنهاد قیمت یا سقف روزانه پایین است.» |
| خرید عقب (bad) | `dev_conv < −25%` | «خرید {dev} عقب است. اگر تا روز ۱۵ جبران نشود، هدف از دست می‌رود — جابه‌جایی بودجه به ردیف دوم تخصیص را بررسی کنید.» |
| در مسیر (ok) | هیچ‌کدام | «کمپین در مسیر پیش‌بینی است.» |

**پیشنهاد جابه‌جایی** (`realloc`): فقط اگر طرح ≥ ۲ ردیف، هزینه > ۰ و `dev_conv ≤ −25%`. ۳۰٪ بودجه‌ی ردیف اول به ردیف دوم منتقل می‌شود و **فقط اگر خرید مورد انتظار بالا برود** پیشنهاد نمایش داده می‌شود: «انتقال ۳۰٪ بودجه‌ی باقی‌مانده از {ردیف ۱} به {ردیف ۲} خرید مورد انتظار را از {x} به {y} می‌رساند.» اعمال آن نسخه‌ی تازه‌ی طرح می‌سازد (دلیل: «پیش از جابه‌جایی حین اجرا»).

«ثبت پایش و ارسال هشدار»: رویداد `pace_logged` + اعلان درون‌برنامه‌ای برای هر هشدار bad (و ایمیل طبق BACKEND-SPEC §۵).

### ۸.۳ درخت تصمیم (`verify`) — اولین شرط برقرار برنده است

```
Δ = (واقعی − پیش‌بینی) / پیش‌بینی   (اگر پیش‌بینی ۰ باشد → ۰)
ΔB بودجه · ΔI نصب · ΔC خرید · ΔCVR = Δ(خرید÷نصب)
fraud = fraud_pct / 100

۱) data_complete = خیر  یا  tracker_matched = خیر  یا  attribution_window ≠ rules.attr_window
      → «ناسازگاری داده» · کالیبراسیون ✕ · توقف
   یا fraud > rules.fraud_th
      → «ناسازگاری داده» · کالیبراسیون ✕

۲) |ΔB| > exec_th
      → «انحراف اجرا» · کالیبراسیون ✕

۳) |ΔB| > 0.02  و  scale_lo ≤ ΔI/ΔB ≤ scale_hi  و  |ΔCVR| ≤ 0.15
      → «مقیاس، نه کیفیت» · کالیبراسیون ✕

۴) |ΔI| > est_th  یا  |ΔCVR| > est_th
      → «خطای برآورد» · ✅ کالیبراسیون

۵) در غیر این صورت
      → «در دامنه‌ی انتظار» · ✅ کالیبراسیون
```

| علت | توضیح (`expl`) | دلیل عدم کالیبراسیون (`block`) |
|---|---|---|
| ناسازگاری داده (پنجره) | «پنجره‌ی انتساب نتیجه ({n} روز) با پنجره‌ی طرح ({m} روز) نمی‌خواند؛ مقایسه‌ی پیش‌بینی و واقعی معتبر نیست.» | «ابتدا کیفیت داده، انطباق ترکر و پنجره‌ی انتساب اصلاح شود؛ تا آن زمان نرخ‌ها دست نمی‌خورند.» |
| ناسازگاری داده (ناقص/ترکر) | «داده‌ی ناقص یا شناسه‌ی ترکر نامنطبق، هر تفسیری از انحراف را بی‌اعتبار می‌کند.» | همان |
| ناسازگاری داده (تقلب) | «نرخ نصب مشکوک به تقلب {x}٪ است، بالاتر از آستانه‌ی {y}٪. نصب‌ها قابل اتکا نیستند.» | «نصب تقلبی نرخ کانال را به‌طور مصنوعی بهتر نشان می‌دهد؛ کالیبراسیون با این داده حافظه را آلوده می‌کند.» |
| انحراف اجرا | «بودجه‌ی مصرف‌شده با طرح نمی‌خواند ({ΔB})؛ پیش از قضاوت درباره‌ی برآورد، اجرا بررسی شود.» | «انحراف از اجرا آمده، نه از نرخ؛ کالیبره‌کردن در این حالت حافظه‌ی سیستم را با نویز خراب می‌کند.» |
| مقیاس، نه کیفیت | «کمپین بزرگ‌تر یا کوچک‌تر از طرح اجرا شد (بودجه {ΔB}، نصب {ΔI}) و CVR ثابت ماند ({ΔCVR})؛ کارایی تغییر نکرده.» | «نسبت انحراف نصب به بودجه نزدیک یک و CVR پایدار است؛ نرخ کانال غلط نبوده.» |
| خطای برآورد | «بودجه طبق طرح خرج شد ({ΔB}) ولی خروجی نخواند — نصب {ΔI}، CVR {ΔCVR}؛ نرخ‌ها باید اصلاح شوند.» | — |
| در دامنه‌ی انتظار | «بودجه و خروجی داخل دامنه‌ی انتظار ماندند؛ مشاهده به‌عنوان نمونه‌ی معتبر به نرخ‌ها اضافه می‌شود.» | — |

> ⚠ **ظریف‌ترین قاعده‌ی کل سیستم:** وقتی انحراف از **داده**، **اجرا** یا **مقیاس** آمده، نرخ کانال غلط نبوده. کالیبره‌کردن در آن حالت حافظه‌ی سیستم را با نویز خراب می‌کند. اگر فقط یک چیز را دقیق پیاده کنید، همین است.

### ۸.۴ بودن داخل بازه (`within_band`) — فقط مسیر متصل

برای نصب، خرید و درآمد: `low ≤ actual ≤ high` از `simulation`. روی کارت: «واقعی حتی از کران پایین پیش‌بینی هم پایین‌تر بود.» یا «واقعی داخل بازه‌ی تجربی افتاد.» (این فیلد در نمونه پیاده نشده — بخش ۱۸.)

### ۸.۵ اثر افزایشی (incrementality)

```
treated = actual_conversions / reach
lift    = (treated − holdout_cvr) / treated          (اگر هر دو > ۰)
```

| حالت | متن |
|---|---|
| گروه کنترل ثبت نشده | «گروه کنترل ثبت نشده — اثر افزایشی قابل سنجش نیست؛ بخشی از خریدها ممکن است ارگانیک باشد.» |
| `lift ≤ 0` | «گروه کنترل به همان اندازه خرید داشت — اثر افزایشی کمپین صفر یا منفی است.» |
| `lift > 0` | «{lift}٪ از خریدها افزایشی است؛ بقیه بدون کمپین هم اتفاق می‌افتاد.» |

مثال: reach ۵۰٬۰۰۰، خرید ۵۹۰، کنترل ۰٫۴٪ → treated ۱٫۱۸٪ → lift ≈ ۶۶٪.

### ۸.۶ کالیبراسیون وزنی — فقط شاخه‌ی ۴ و ۵

```
clean_installs = actual_installs × (1 − fraud)
obs_cpi = actual_spend / clean_installs
obs_cvr = actual_conversions / clean_installs

typical   = max(0.4 × ceiling × unit_cost, 1)
w_new     = clamp(actual_spend / typical, 0.3, 3)        ← اندازه‌ی کمپین
w_old     = sample_n × 0.9 ^ age_months                  ← کاهش وزن نمونه‌های قدیمی
seasonal  = seasonal ? (1 + seasonal_lift) : 1
o_cpi     = obs_cpi / infl(r) × seasonal                 ← پاک‌کردن تورم و فصل
o_cvr     = obs_cvr / seasonal

unit_cost_new = round((unit_cost × w_old + o_cpi × w_new) / (w_old + w_new))
cvr_new       = round6((cvr × w_old + o_cvr × w_new) / (w_old + w_new))
sample_n_new  = sample_n + 1 ؛  age = 0 ؛  observed_at = امروز ؛  source = calibration
```

- **پیش‌نمایش پیش از اعمال:** «✅ در این شاخه کالیبراسیون معتبر است — {پیش‌نمایش}» و دکمه‌ی «اعمال کالیبراسیون».
- **فقط مالک و تحلیل‌گر** اعمال می‌کنند. نقش دیگر: «کالیبراسیون در این شاخه معتبر است ولی نقش «{نقش}» اجازه‌ی اعمال آن را ندارد.»
- **بازگردانی:** ۱۰ کالیبراسیون آخر قابل بازگردانی‌اند؛ فقط **جدیدترین** کالیبراسیون هر ردیف. ردیف `before` کامل ذخیره و بازگردانده می‌شود.
- **مثال مرجع (T1 روی یکتانت|فعال):** قبل: CPI ۵۰٬۰۰۰، CVR ۱۳٫۵٪، n=۷، age=۳ → `w_new` ≈ ۲٫۸۹، `w_old` ≈ ۵٫۱۰ → بعد: **CPI ۵۷٬۶۲۹، CVR ۱۱٫۸۵٪، n=۸**. (عدد «۵۸٬۸۰۰» در کارت نمونه‌ی v5 تقریبی بود.)

### ۸.۷ برنامه‌های چندردیفی (قاعده‌ی تازه — در نمونه نبود)

نمونه نتیجه‌ی واقعی را فقط برای **یک** کانال/سگمنت می‌گیرد، حتی وقتی طرح چند ردیف دارد، و کل مشاهده را به ردیف اول نسبت می‌دهد. در تولید:

1. اگر نتیجه به تفکیک ردیف موجود است (ادتریس/اینترک)، درخت تصمیم **برای هر ردیف جدا** اجرا و هر ردیف جدا کالیبره می‌شود؛ علت کل = بدترین علت بر اساس ترتیب درخت.
2. اگر فقط جمع کل موجود است و طرح بیش از یک ردیف دارد: علت محاسبه می‌شود ولی **کالیبراسیون اعمال نمی‌شود** با دلیل «نتیجه به تفکیک ردیف ثبت نشده؛ نسبت‌دادن کل مشاهده به یک ردیف حافظه را آلوده می‌کند.»

```
│  [توضیح هوشمند — اختیاری، از verify_narrative]    │
├──────────────────────────────────────────────────┤
│  دیدگاه انتخاب‌شده: مدیر مالی                     │
│  منبع پیش‌بینی: ایستگاه ۳ (sim_id) | مسیر دستی     │
│  کیفیت داده: تقلب ۳٪ · پنجره ۷ روز · کامل · منطبق │
│  اثر افزایشی (گروه کنترل): {lift_text}            │
│  ← کالیبراسیون: CPI یکتانت|فعال از ۵۰٬۰۰۰ به ۵۷٬۶۲۹│
└──────────────────────────────────────────────────┘
```

**ردیف «دیدگاه انتخاب‌شده» ارزشمندترین جزء کارت است:** بعد از بیست کمپین می‌شود پرسید کدام دیدگاه بیشتر درست از آب درآمده.

## ۹. بستن حلقه و دفترچه‌ی دیدگاه‌ها

### ۹.۱ بستن کمپین

پیش‌شرط: طرح + راستی‌آزمایی. رکورد `perspective_log`:

| فیلد | محاسبه |
|---|---|
| `perspective` · `reason` | از طرح |
| `cause` · `calibrated` | از راستی‌آزمایی |
| `planned_cac` | `sim.CAC` |
| `actual_cac` | `actual_spend / actual_conversions` |
| `actual_poas` | `(actual_conversions × AOV_w × margin − actual_spend) / actual_spend` — AOV وزنی طرح (بخش ۱۸) |
| `goal_hit` | متریک واقعی هدف ≥ `goal_value` (بخش ۱۸) |
| `lift` | از راستی‌آزمایی |

وضعیت کمپین → بسته‌شده؛ رویداد `campaign_closed`؛ اعلان «کمپین {id} بسته و در دفترچه ثبت شد.»؛ اولین بستن غیر دمو پیام جشن «اولین حلقه بسته شد.» را نشان می‌دهد.

### ۹.۲ کیفیت تصمیم هر دیدگاه

```
تصمیم درست = POAS واقعی ≥ 0  و  علت ∉ {انحراف اجرا، ناسازگاری داده}
             (برای ردیف‌های دموی بدون POAS: planned_cac / actual_cac − 1 به‌عنوان جایگزین)
خطای پیش‌بینی = میانگین |actual_cac / planned_cac − 1|
مرتب‌سازی: نسبت تصمیم درست نزولی، سپس تعداد نزولی
```

نمایش هر گروه: «تصمیم درست {g} از {n} · خطای پیش‌بینی {±e}» و اگر n < ۳: «· نمونه کم».
یادداشت الزامی: «تصمیم درست = POAS نامنفی و انحراف قابل انتساب. فقط دیدگاه‌های انتخاب‌شده سنجیده می‌شوند (سوگیری انتخاب).»

## ۱۰. خروجی‌ها

### ۱۰.۱ گزارش کمپین (یک برگ، چاپ/PDF/CSV/JSON)

بخش‌ها: سربرگ (نام، مرچنت، هدف کسب‌وکار، حاشیه، بازه) · زنجیره‌ی شناسه (`plan_id → sim_id → run_id → calibration_id`) · **۱ تصمیم انسان** (دیدگاه، دلیل، هدف) · **۲ تخصیص و شاهدش** (برچسب، بودجه، سهم، CAC، `rates: …· n=…`) · **۳ پیش‌بینی با بازه** (نصب، خرید، درآمد، CAC + ROAS، دو حکم) · **۴ نتیجه‌ی واقعی و انتساب علت** · **۵ اثر روی حافظه‌ی سیستم** («ردیف X: CPI از a به b · CVR از … · sample_n از … به …» یا «کالیبراسیونی اعمال نشده — شاخه‌ی «…» عمداً نرخ‌ها را دست نمی‌زند.»).
پانویس الزامی: «همه‌ی اعداد این گزارش از جدول نرخ‌های ثبت‌شده آمده‌اند. بازه‌ها برون‌یابی نوسان تاریخی همان کانال‌اند، نه خروجی یک مدل.»
لینک اشتراک: URL امضاشده‌ی فقط‌خواندنی، فقط برای کاربر با ایمیل تأییدشده.

### ۱۰.۲ داشبورد ذی‌نفع — چهار نما (`?view=cfo|ceo|analyst|ops`)

| نما | کارت‌ها (با `source_ref`) | فهرست |
|---|---|---|
| مدیر مالی | CAC کل در برابر سقف حاشیه · POAS کل · کمپین‌های ضررده در سطح واحد · CAC هدف مرچنت | سود واحد هر کانال (درآمد − هزینه) |
| مدیرعامل | حجم کل خروجی · درآمد کل · بیشترین سهم کانال · فاصله تا هدف کمپین بعدی | روند خرید ماهانه |
| تحلیل‌گر داده | میانگین نوسان جدول نرخ · ردیف‌های کم‌نمونه (n<۵) · کیفیت داده‌ی تاریخی (سهم منبع اسمارتک) · کل نمونه‌های پشت نرخ‌ها | پرنوسان‌ترین ۷ ردیف |
| مسئول کمپین | کمپین‌های ثبت‌شده · کارت انحراف باز · آشناترین ردیف · کالیبراسیون اعمال‌شده | تعداد کمپین هر کانال |

+ کارت «مقایسه با میانه‌ی صنعت» (فقط اگر `n_merchants ≥ 10`؛ در نمونه با ضریب ساختگی).
**هیچ عدد جدیدی ساخته نمی‌شود؛ همان داده از زاویه‌ی هر نقش.**

### ۱۰.۳ روش‌شناسی

نه بخش (تورم، پولی/خودی، بازده نزولی، شاخص‌های مالی، بازه‌ی تجربی، درخت تصمیم، اثر افزایشی، کالیبراسیون وزنی، کیفیت تصمیم) + «محدودیت‌های شناخته‌شده». آستانه‌ها **زنده** از `rules` خوانده می‌شوند. متن عیناً از نمونه.

### ۱۰.۴ پرسش از داده (Ask)

«به فارسی بپرسید؛ پاسخ فقط از جدول نرخ ساخته می‌شود و منبعش کنارش می‌آید. اگر پرسش به یک عدد مشخص نگاشت نشود، سیستم عدد نمی‌سازد.»

| intent | پرسش نمونه | پرس‌وجوی قطعی | پاسخ قالبی |
|---|---|---|---|
| `cheapest_cac` | ارزان‌ترین کانال کدام است؟ | کمترین `cac` | «کمترین CAC متعلق به {ch} روی «{seg}» است: {x} تومان (با تعدیل تورم).» |
| `most_expensive_cac` | گران‌ترین جذب کجاست؟ | بیشترین `cac` | «گران‌ترین جذب: {ch} روی «{seg}» با CAC {x} تومان.» |
| `most_stable` | پایدارترین ردیف؟ | کمترین `variance` | «پایدارترین ردیف {ch} / {seg} با نوسان ±{x} است.» |
| `best_retention` | بیشترین ماندگاری روز ۳۰؟ | بیشترین `d30` | «بیشترین ماندگاری روز ۳۰: {ch} / {seg} با {x}.» |
| `highest_fraud` | نرخ تقلب کجا بالاست؟ | بیشترین `fraud` | «بیشترین نرخ تقلب در {ch} است: {x} از نصب‌ها.» |
| `best_poas` | کدام ردیف سودآورتر است؟ | بیشترین `(aov×margin×cvr − cpi_adj)/cpi_adj` | «سودآورترین ردیف در سفارش اول: {ch} / {seg} با POAS {x}.» |
| `channel_summary` | وضعیت تپسل | ردیف‌های کانال، بهترین CAC | «{ch} در {k} سگمنت داده دارد؛ بهترین CAC روی «{seg}»: {x} تومان.» |
| `channel_segment` | CAC یکتانت روی کاربر جدید چند است؟ | ردیف دقیق | «{ch} روی «{seg}»: CAC {x} تومان، CVR {y}، نوسان ±{z} (n={n}).» — **تازه** (در نمونه نبود) |
| `unsupported` | فروش ماه بعد چقدر می‌شود؟ | — | «این پرسش به یک عدد مشخص در جدول نرخ نگاشت نشد. لایه‌ی ۲ حق ساختن عدد ندارد؛ یکی از پرسش‌های پیشنهادی را امتحان کنید.» |

هر پاسخ: `{text, source_refs[], grounded}`؛ منبع زیر پاسخ: `rates: {ch}|{seg} · n={n}`.

## ۱۱. لایه‌ی ۲ — هوش مصنوعی با متیس

### ۱۱.۱ اصل

- **لایه‌ی ۱ هر عدد را می‌سازد.** مدل زبانی فقط: پرسش را می‌فهمد، توضیح فارسی می‌نویسد، ستون‌های CSV را نگاشت می‌کند، خلاصه می‌کند.
- مدل هیچ عددی نمی‌گوید که در ورودی‌اش نبوده. **سرور این را اجرا می‌کند، نه پرامپت.** پرامپت فقط احتمال خطا را کم می‌کند.
- هر سطح هوش مصنوعی یک جایگزین قطعی دارد. خاموش‌بودن متیس هیچ خطایی در رابط ایجاد نمی‌کند.

### ۱۱.۲ اتصال به متیس

- متیس APIای سازگار با OpenAI دارد: SDK رسمی `openai` با `baseURL = METIS_BASE_URL`.
- متغیرها: `AI_PROVIDER=mock|metis` · `METIS_API_KEY` · `METIS_BASE_URL` (پیش‌فرض `https://api.metisai.ir/openai/v1`، باید از پنل متیس تأیید شود) · `METIS_MODEL_FAST` · `METIS_MODEL_SMART` · `AI_TIMEOUT_FAST_MS=8000` · `AI_TIMEOUT_SMART_MS=20000`.
- **نقطه‌ای که کلید متیس لازم است: مرحله‌ی M7.** تا آن زمان همه‌چیز روی `mock` ساخته و آزموده می‌شود.

### ۱۱.۳ هفت وظیفه

پرامپت سیستمی کامل هر وظیفه در `packages/ai/prompts/<task>.v1.md` نوشته شده است (قواعد مشترک در `_shared.v1.md`).

| # | وظیفه | مدل | کجا در حلقه | خروجی | جایگزین قطعی |
|---|---|---|---|---|---|
| ۱ | `ask_intent` | fast | پرسش از داده | `{intent, channel, segment, metric}` | تطبیق regex نمونه (`answer`) |
| ۲ | `ask_phrase` | fast | پرسش از داده | `{text, source_refs[]}` | جمله‌ی قالبی ۱۰.۴ |
| ۳ | `insight_explain` | fast | کارت اینسایت | `{why, risk}` هرکدام ≤ ۲ جمله | متن ثابت کارت |
| ۴ | `verify_narrative` | smart | کارت راستی‌آزمایی | `{summary, next_step}` | `expl` + `block` شاخه |
| ۵ | `csv_map` | fast | آپلود CSV | `{mapping, confidence, warnings[]}` | تطبیق دقیق نام ستون؛ کاربر در پیش‌نمایش تأیید می‌کند |
| ۶ | `monthly_summary` | smart | گزارش ماهانه‌ی ایمیلی | `{headline, bullets[3]}` | فهرست KPI قالبی |
| ۷ | `plan_reason_hint` | fast | فیلد دلیل انتخاب | `{is_specific, hint}` | بدون راهنما (هرگز مسدود نمی‌کند) |

جریان Ask: `پرسش → ask_intent → پرس‌وجوی قطعی روی rates → ask_phrase(ردیف‌ها) → دیوار عدد → رابط`. intent ناشناخته → `grounded:false`، بدون عدد، نمایش پرسش‌های پیشنهادی.

### ۱۱.۴ نگهبان‌های سمت سرور (اجباری)

1. **خروجی ساخت‌یافته:** `response_format: json_schema` اگر مدل پشتیبانی کند، وگرنه JSON mode. اعتبارسنجی با zod؛ در شکست یک تلاش دوباره با متن خطا، سپس جایگزین.
2. **دیوار عدد:** رقم فارسی/عربی، `٬` `٫` `%` `٪` نرمال می‌شوند؛ هر عدد در متن خروجی باید با یک عدد در `facts` ورودی بخواند (±۰٫۵٪، یا تبدیل واحد مستند مثل «۵۰۰ م» = ۵۰۰٬۰۰۰٬۰۰۰ و «۱٫۵ میلیارد»). عدد ناشناخته → رد → جایگزین → `llm_call.status = violation`.
3. **`source_refs`** همه باید در ورودی وجود داشته باشند.
4. **بدون اطلاعات شخصی:** فقط تجمیع، نام کانال/سگمنت، شناسه. بدون ایمیل، نام شخص، کلید.
5. **زمان و تلاش دوباره:** یک تلاش دوباره با jitter. **قطع‌کن مدار:** ۵ شکست در ۶۰ ثانیه → ۱۲۰ ثانیه باز → جایگزین.
6. **کش:** کلید `sha256(task, prompt_version, model, context)` در Redis، ۲۴ ساعت.
7. **بودجه‌ی توکن ماهانه:** آزمایشی ۲۰۰ هزار · رشد ۲ میلیون · سازمانی سفارشی؛ عبور از سقف → جایگزین + یک اعلان.
8. **محدودیت نرخ:** Ask ۳۰ در دقیقه برای هر کاربر.
9. **پرچم** `workspace.ai_enabled` (پیش‌فرض روشن). متن مدل با برچسب «توضیح هوشمند» و همیشه با تراشه‌ی منبع.
10. **واژه‌های ممنوع در خروجی مدل:** «فاصله‌ی اطمینان»، «سطح اطمینان»، «دقیق است»، «هوشمند است»، «شبیه‌سازی می‌کند»، «تضمین». اگر آمد → رد.

### ۱۱.۵ قرارداد ورودی مدل (مشترک همه‌ی وظیفه‌ها)

ورودی هر وظیفه یک شیء JSON است که **فقط** از خروجی لایه‌ی ۱ ساخته می‌شود و یک آرایه‌ی `facts` دارد:

```json
{
  "facts": [
    { "ref": "rates:یکتانت|فعال#cac", "label": "CAC", "value": 385000, "display": "۳۸۵٬۰۰۰ تومان" },
    { "ref": "sim:sim-1405-101#poas", "label": "POAS", "value": 0.658, "display": "+۶۶٪" }
  ]
}
```

مدل موظف است هر عدد را **عیناً با همان `display`** بنویسد. دیوار عدد هر دو شکل `value` و `display` را می‌پذیرد. این کار خطای گرد‌کردن و تبدیل واحد را از بین می‌برد.

### ۱۱.۶ ثبت فراخوانی‌ها

```
llm_call(id, workspace_id, user_id, task, prompt_version, provider, model, latency_ms,
         tokens_in, tokens_out, cost_toman, status[ok|cached|fallback|violation|error|timeout],
         error_code, created_at)
```

متن خام پرامپت و پاسخ فقط با `AI_DEBUG=true` و فقط در محیط توسعه. نمای مدیر: فراخوانی روزانه، نرخ جایگزین، نرخ تخلف، p95 تأخیر، هزینه.

### ۱۱.۷ ارزیابی

- `fixtures/ai-evals.jsonl` — ۳۶ پرسش با intent/کانال/سگمنت مورد انتظار.
- `pnpm ai:eval` — روی mock و (در صورت وجود کلید) متیس. دروازه‌ی CI: دقت intent ≥ ۹۰٪، **تخلف عدد = ۰**، شکست schema < ۲٪.
- `pnpm ai:smoke` — هر وظیفه یک بار با داده‌ی seed؛ چاپ تأخیر، توکن، قبول/رد.

1. **B18 — کانال خودی در دیدگاه‌های حجم‌محور:** آیا `ceo` و `cmo` باید پوش/پیامک را جدا از جذب پولی رتبه‌بندی کنند؟ امروز چهار دیدگاه در دمو تخصیص تقریباً یکسان می‌دهند و «تنوع دیدگاه» ضعیف دیده می‌شود.
2. **B19 — تقلب در کارت اینسایت:** «خرید مورد انتظار» کارت با تقلب کم شود تا با Simulator یکی باشد؟
3. **B20 — هدف «نگهداشت»:** به خرید نگاشت شود (رفتار فعلی) یا به کاربران ماندگار روز ۳۰ (`ret30`)؟
4. **B9 و B11 — دو تغییر متن** در کارت مدیر بازاریابی و عنوان «دقیق‌ترین دیدگاه»: تأیید می‌کنید؟
5. **B14 — توقف خودکار کمپین‌ها:** فقط هم‌کانال/سگمنت یا همه؟
6. **کالیبراسیون خودکار** برای شاخه‌ی «در دامنه‌ی انتظار»، به‌صورت گزینه‌ی فضای کاری با پیش‌فرض خاموش؟
7. **`ceo` و تورم:** امتیاز مدیرعامل از CPI بدون تعدیل تورم استفاده می‌کند؛ حفظ شود؟
8. **کانال «سایر»** که در v5 بود و در نمونه نیست: برگردد؟
9. **متیس:** نام دقیق مدل‌های fast و smart، و اینکه `json_schema` در `response_format` پشتیبانی می‌شود یا فقط JSON mode.
